# Feature Specification: V1 Completion — GUI, Starter Packs, IP Fallback, and Gap Closure

**Feature Branch**: `007-v1-completion`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "create a new spec 7 that includes the resolution to all gaps and
the features that I want included FR-22, 7, 12 — a native GUI settings app (PRD FR-22), bundled
starter pack(s) (PRD FR-7), and IP-geolocation location fallback (PRD FR-12), all previously
`[Future]`-tagged and deferred out of the PRD's 6-spec breakdown, now explicitly requested for
the shippable product — plus closing the documented, still-open reliability/verification gaps
left over from specs 3, 5, and 6 (output hotplug/resize/disconnect test coverage, packaging's
GeoClue soft-dependency, and the manual-QA-only verification items neither automated testing nor
this project's own dev environment could close on their own)."

## Clarifications

### Session 2026-08-14

- Q: Should the GUI ship as its own standalone libcosmic application, or as a panel embedded
  inside `cosmic-settings`? → A: Standalone application. COSMIC does not currently expose a
  general, documented extension mechanism for third-party `cosmic-settings` panels — every
  comparable community project targeting COSMIC (and this project's own `wallpaperctl`, spec 4)
  ships as its own binary. Constitution Principle IX requires libcosmic widgets and shared
  theme tokens either way, which a standalone app satisfies exactly the same as a panel would.
  This is a platform-capability-driven default, not a coin flip — resolved here rather than left
  as a marker, so it doesn't consume this spec's limited clarification budget.
- Q: How many starter packs should ship, and where does the image content come from? → A:
  One pack, procedurally-generated gradient/sky art — no photography, and therefore no
  per-image licensing verification burden at all. Smallest package size of the three options
  considered, and zero licensing risk since every asset is generated by the project itself
  rather than sourced from a third party (see FR-009).
- Q: Should IP-based location call a third-party network API at resolution time, or use a
  bundled/periodically-updated offline database queried locally? → A: A bundled, periodically-
  updated offline database. No outbound network call is made per resolution — consistent with
  spec 6's already-established privacy-conscious defaults (coarsest-accuracy requests,
  opt-in-only automatic location) rather than introducing this spec's one third-party network
  dependency (see FR-014).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Configure Everything Without the CLI (Priority: P1)

A user opens a native COSMIC settings application instead of a terminal to browse available
wallpaper packs with previews, assign a pack to a specific output (or turn on "same pack
everywhere"), enter or clear a manual location, toggle automatic (portal-based) location, adjust
crossfade duration, and see a timeline of what will show throughout today.

**Why this priority**: PRD FR-22 was the top explicitly-requested item, and the constitution
itself treats CLI-only control as an *interim* substitute for early milestones (Principle IX) —
this closes that gap and is this spec's single largest piece of new user-facing surface area.

**Independent Test**: With at least one pack already registered (via the CLI or a starter pack,
User Story 2) and an output connected, complete a full "browse a pack, assign it, set a
location, see it on the timeline" flow entirely inside the GUI, with no terminal command run at
any point.

**Acceptance Scenarios**:

1. **Given** one or more registered packs, **When** the user opens the GUI's pack browser,
   **Then** each pack is shown with an image preview, matching what spec 2's loader validated.
2. **Given** a pack and a connected output, **When** the user assigns that pack via the GUI,
   **Then** the assignment is written to the same `RendererConfig` spec 3/4 already use — a
   concurrently-running `wallpaperctl assign` and the GUI never disagree about current state,
   since both read/write the identical `cosmic-config` entry.
3. **Given** the GUI's location panel, **When** the user enters a manual location, toggles
   automatic (portal) location, or (User Story 3) enables IP-based location, **Then** the change
   is written to the same `LocationConfig` schema spec 6 already defines — exactly one mode
   active at a time, same as the CLI's existing behavior.
4. **Given** an output with an active schedule, **When** the user views the GUI's timeline for
   today, **Then** it shows the same active-image/next-transition data `wallpaperctl query`
   already reports, not a separately-computed value.
5. **Given** the GUI's crossfade duration control, **When** the user changes it, **Then** the new
   duration applies to subsequent transitions without restarting `wallpaperd` (reusing spec 3's
   existing live-config-watch behavior).

### User Story 2 - Get Something Beautiful With Zero Configuration (Priority: P2)

A user who just installed the package sees a real dynamic wallpaper actively transitioning
through the day immediately, without registering, assigning, or configuring anything.

**Why this priority**: Directly serves PRD Goal G4 ("feels like a native part of COSMIC —
install, configure, and forget") and Goal G1's zero-configuration path, but a user who already
has their own pack (Stories elsewhere) doesn't need this to get full value from the project.

**Independent Test**: On a freshly-installed system with no prior `wallpaperctl` commands ever
run, confirm a bundled starter pack is already registered, assigned, and actively scheduled.

**Acceptance Scenarios**:

1. **Given** a fresh install, **When** `wallpaperd` first starts, **Then** at least one bundled
   starter pack is already known to the registry (spec 2) and assigned to every connected output
   with no explicit assignment (same fallback tier spec 3's "same pack everywhere"/default
   assignment logic already defines), with no `wallpaperctl register`/`assign` ever run.
2. **Given** a user who explicitly removes a bundled starter pack (`wallpaperctl remove` or the
   GUI's equivalent), **When** the package is later upgraded, **Then** that pack is **not**
   silently re-registered — an explicit removal is permanent, the same posture Debian package
   management already takes toward user-modified state.
3. **Given** a user who has already registered and assigned their own pack before ever seeing a
   starter pack take effect, **When** `wallpaperd` starts, **Then** the user's own assignment
   takes precedence — a starter pack never overrides an explicit user choice.

---

### User Story 3 - Get Automatic Scheduling Without a Location Portal (Priority: P3)

A user on a system where the location portal isn't available (or chooses not to use it) and who
doesn't want to type coordinates gets an approximate location automatically via IP-based
geolocation, as an explicit, opt-in third option alongside spec 6's automatic (portal) mode and
spec 4's manual entry.

**Why this priority**: PRD's own FR-12 text calls this "a weaker privacy story" that "shouldn't
be the default" — real value for users blocked on both other paths, but strictly the
lowest-priority of this spec's three new capabilities, matching the PRD's own risk framing even
though it's now in scope.

**Independent Test**: With no manual location set and the portal unavailable or declined, enable
IP-based location and confirm a solar-anchored pack schedules against the resolved approximate
location, without any coordinates typed and without the portal ever being involved.

**Acceptance Scenarios**:

1. **Given** no manual location and no working portal resolution, **When** the user explicitly
   enables IP-based location, **Then** an approximate location is resolved and used for solar
   scheduling — never enabled implicitly, matching spec 6's existing opt-in-by-default posture
   for automatic location.
2. **Given** IP-based location is enabled, **When** the resolution fails (offline, blocked,
   service unreachable), **Then** the system degrades exactly the way spec 6's FR-005 already
   requires for portal failures — fall back to manual if set, else the existing no-location
   behavior — no new failure mode invented.
3. **Given** IP-based location, portal-automatic location, and manual location are all
   configured at different times, **When** the user checks which is active, **Then** exactly one
   mode is active at a time (extends spec 6's existing `LocationMode` with a third variant,
   never a silent multi-source fallback chain).

---

### User Story 4 - Harden and Verify Already-Shipped Specs Before Release (Priority: P1)

The project closes its own previously-documented, still-open reliability and verification gaps
from specs 3, 5, and 6 — so that calling the product "shippable" rests on evidence, not on
caveats left in a README.

**Why this priority**: These are the gaps standing between "specs 1–6 implemented" and
"confidently shippable" today — equal in priority to the GUI (User Story 1), since neither a
beautiful settings app nor bundled content matters if the underlying daemon's hotplug handling
or install path has an unverified failure mode.

**Independent Test**: Run the project's automated test suite and confirm output hotplug/resize/
disconnect scenarios are exercised without any physical display hardware attached; separately,
confirm each remaining manual-QA-only gap has documented, dated evidence of having been executed
at least once.

**Acceptance Scenarios**:

1. **Given** the project's test suite, **When** it runs in an environment with no physical
   display attached, **Then** output connect, disconnect, and resize scenarios are all exercised
   and pass — closing spec 3's previously-unimplemented mock hotplug test harness.
2. **Given** the project's Debian packaging metadata, **When** it's built, **Then** it declares
   GeoClue2 as a recommended (never required) dependency — closing spec 6 research.md's flagged,
   previously-unapplied packaging suggestion, without breaking installs on systems that don't
   carry it (spec 6 FR-005's existing degrade path still applies).
3. **Given** the manual-QA-only gaps that no automated harness in this environment can close
   (spec 5's real install/autostart/crash-restart lifecycle on a live session; spec 6's full
   automatic-location success path against a real GeoClue backend with location services
   enabled), **When** this spec is considered complete, **Then** each has been executed at least
   once against real, qualifying hardware/environment, with dated results recorded in the
   project's documentation — not left as an open caveat indefinitely.

### Edge Cases

- What happens if the GUI and a concurrent `wallpaperctl` command modify the same setting at
  nearly the same time? No new locking is introduced — both read/write the identical
  `cosmic-config` entries specs 3/4/6 already define, and the daemon's existing change-
  coalescing (spec 3 FR-014) already resolves rapid successive changes to a well-defined
  outcome; this spec does not add a second concurrency story.
- What happens if a bundled starter pack's image files are later deleted or corrupted on disk?
  Falls back to spec 2's existing `Unavailable`-pack handling — no special case invented for
  starter packs specifically.
- What happens if IP-based location is enabled while the machine is offline? Same graceful
  degrade as any other portal/network failure (spec 6 FR-005) — no hang, no crash.
- What happens when the automated hotplug/resize/disconnect test harness's simulated behavior
  doesn't perfectly match every real compositor's actual event sequence? The harness closes the
  *previously entirely untested* branches with fast, repeatable coverage — it's a floor, not a
  total replacement for occasional real-hardware spot checks; this spec doesn't claim it
  eliminates all future need for manual QA on that surface, only that it closes the specific
  "never tested at all" gap.
- What happens if a user's system has neither a location portal, no manual entry, and declines
  IP-based location too? Existing no-location behavior for solar-anchored packs applies
  unchanged (spec 1's contract) — clock-anchored packs remain fully usable regardless.

## Requirements *(mandatory)*

### Functional Requirements

**GUI (User Story 1, PRD FR-22)**

- **FR-001**: The system MUST provide a native GUI settings application, built with libcosmic
  widgets and shared COSMIC theme tokens (constitution Principle IX), shipped as its own
  standalone application (Clarifications).
- **FR-002**: The GUI MUST let a user browse registered packs with an image preview per pack.
- **FR-003**: The GUI MUST let a user assign a pack to a specific output, or enable "same pack
  everywhere," writing to the same configuration spec 3/4 already read and write.
- **FR-004**: The GUI MUST let a user enter, view, or clear a manual location, and switch between
  manual, automatic (portal), and (User Story 3) IP-based location modes.
- **FR-005**: The GUI MUST let a user view a timeline visualization of the current day's schedule
  per output, reflecting the same live state `wallpaperctl query` already reports.
- **FR-006**: The GUI MUST let a user adjust crossfade duration, applied live without requiring a
  `wallpaperd` restart.
- **FR-007**: The GUI and the existing CLI (spec 4) MUST remain interchangeable, never-conflicting
  control surfaces over the same persisted state — neither is authoritative over the other.

**Starter Packs (User Story 2, PRD FR-7)**

- **FR-008**: The project MUST bundle at least one wallpaper pack that is automatically
  registered and assigned on a fresh install, with zero user configuration required to see a
  real dynamic wallpaper actively transitioning.
- **FR-009**: The bundled starter pack MUST consist of procedurally-generated gradient/sky art
  (no photography, no third-party image content) — one pack, spanning a solar-anchored day cycle
  (Clarifications), eliminating per-image licensing verification entirely since every asset is
  generated by the project itself.
- **FR-010**: A user's explicit removal of a bundled starter pack MUST be permanent — a later
  package upgrade MUST NOT silently re-register it.
- **FR-011**: A starter pack's default assignment MUST NOT override a user's own explicit
  assignment made before or after install.

**IP-Geolocation Fallback (User Story 3, PRD FR-12)**

- **FR-012**: The system MUST support resolving an approximate location via IP-based
  geolocation, as a third location mode alongside spec 6's automatic (portal) and spec 4's
  manual modes — extending spec 6's existing `LocationMode` rather than introducing a parallel
  fallback-chain mechanism (mutually exclusive, one active mode at a time, per Assumptions).
- **FR-013**: IP-based location MUST default to OFF and require an explicit user opt-in — never
  enabled implicitly, matching spec 6's existing privacy-default posture for automatic location.
- **FR-014**: IP-based location MUST be resolved via a bundled, periodically-updated offline
  IP-to-location database queried locally (Clarifications) — never a third-party network API
  call at resolution time, so opting in never discloses a request to an external service.
- **FR-015**: IP-based location resolution failure (offline, blocked, unreachable) MUST degrade
  exactly the way spec 6 FR-005 already requires for portal failures — no new failure mode.

**Gap Closure (User Story 4)**

- **FR-016**: The project MUST include an automated test harness simulating output connect,
  disconnect, and resize events without requiring physical display hardware, closing spec 3's
  previously-unimplemented mock hotplug harness (spec 3 tasks.md T043).
- **FR-017**: Output disconnect and resize-triggered reconfiguration MUST be covered by passing
  automated tests using that harness — closing the previously-untested branches in spec 3's
  output-update handling.
- **FR-018**: The project's Debian packaging metadata (spec 5) MUST declare GeoClue2 as a
  recommended, never required, dependency (spec 6 research.md's flagged, previously-unapplied
  cross-spec suggestion) — an install without it MUST still succeed and behave per spec 6
  FR-005's existing degrade path.
- **FR-019**: Every remaining verification gap that automated testing in this project's own
  development environment cannot close (spec 5's real install/autostart/crash-restart lifecycle
  on a live session; spec 6's full automatic-location success path against a real GeoClue
  backend with location services enabled) MUST be executed at least once against qualifying real
  hardware/environment before this spec is considered complete, with dated results recorded in
  the project's documentation.

### Key Entities

- **StarterPack**: A wallpaper pack (spec 2's existing `PackRegistryEntry` shape) bundled with
  the project and distinguished by an "installed by package, not by user" origin flag — the only
  new piece of state this spec's registry-facing work needs, used solely to implement FR-010's
  "don't silently re-register after explicit removal" rule.
- **LocationMode (extended)**: Spec 6's existing enum gains a third variant for IP-based
  location, remaining mutually exclusive with `Manual` and `Automatic` (FR-012).
- **GUI Settings Session**: Not a persisted entity — the GUI reads and writes exactly the
  `cosmic-config` entries specs 2/3/4/6 already define (pack registry, `RendererConfig`,
  `LocationConfig`); it introduces no new persisted shape of its own beyond `LocationMode`'s
  extension above.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can complete every configuration task previously requiring the CLI (browse/
  assign packs, set location and its mode, adjust crossfade duration) entirely through the GUI,
  without opening a terminal.
- **SC-002**: A freshly-installed system shows a real, actively-transitioning dynamic wallpaper
  immediately, with zero user configuration steps.
- **SC-003**: A user with neither a working location portal nor a manually-entered location can
  still get an automatically-scheduled solar-anchored pack, using IP-based location alone, opted
  into explicitly.
- **SC-004**: Output hotplug, disconnect, and resize scenarios are covered by an automated test
  suite runnable without physical display hardware — 100% of the previously-manual-only
  scenarios named in spec 3's documented gaps are now also exercised automatically.
- **SC-005**: Every previously-open manual-QA-only verification gap (spec 3's real-hardware
  disconnect/resize spot check, spec 5's install lifecycle, spec 6's GeoClue happy path) has
  dated, recorded evidence of having been executed at least once.
- **SC-006**: A user who explicitly removes a bundled starter pack never sees it reappear after a
  package upgrade.

## Assumptions

- **Scope decision (explicit user direction)**: This spec deliberately combines three
  previously `[Future]`-tagged PRD items (FR-22, FR-7, FR-12) with a release-hardening pass over
  already-shipped specs 3/5/6, per the user's explicit request that all of this land in the
  shippable product — a deliberate departure from the PRD's own "revisit only if usage tells you
  these matter" deferral (PRD §8), not an oversight. Each remains its own independently-testable
  user story specifically so they can still be implemented, tested, and delivered incrementally
  despite being grouped under one spec number.
- **GUI shape (resolves Clarifications)**: standalone libcosmic application, not a
  `cosmic-settings` panel — platform-capability-driven, not a preference call.
- **LocationMode design**: IP-based location extends spec 6's existing single-active-mode enum
  with a third variant, rather than introducing a fallback chain that could try multiple sources
  per resolution — consistent with spec 6's existing design and simpler to reason about.
- **GUI depends on, doesn't replace, the CLI**: spec 4's `wallpaperctl` remains fully supported;
  this spec adds a second control surface over identical state, per constitution Principle IX's
  framing of CLI as an "acceptable substitute... in early milestones" rather than something to be
  removed once a GUI exists.
- **Starter packs install via spec 5's packaging**: registered automatically as part of the
  Debian package's install flow (`postinst`), not requiring any manual `wallpaperctl` step —
  consistent with spec 5's existing maintainer-script-based install model.
- **Gap closure is bounded by what's actually automatable**: FR-016/FR-017 close what a mock
  harness genuinely can simulate; FR-019 requires the remaining truly-environment-dependent items
  be executed and recorded, not that they become automatable — there is no reasonable way to
  automate "does a real Debian package manager install this correctly on real hardware."
- This spec assumes specs 1–6 already exist as implemented (or, for 5–6, at minimum fully
  planned/tasked) dependencies whose existing contracts (schemas, CLI commands, D-Bus interface)
  it consumes and extends rather than redefines.
